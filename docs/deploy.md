# First deploy — Supabase + Render

Order matters: the database role has to exist before the first boot, because
`init_db()` runs on import and immediately checks whether row level security is
actually being enforced.

> **Esto describe cómo levantar un entorno desde cero.** El que ya existe está
> en [`handoff.md`](./handoff.md) → *Coordenadas* (servicio, URL, proyecto de
> Supabase). Si viniste a operar el que está andando, andá ahí.

---

## 1. Supabase

Create the project, then run [`sql/18_supabase_setup.sql`](../sql/18_supabase_setup.sql)
in the SQL Editor. It creates `kikar_app`, the role the application connects
as, and ends with two checks worth reading rather than skipping:

- `rolbypassrls` must be **false**. If it is true, the isolation policies are
  inert and one JCC can read another's data.
- `LISTEN` must not error. Supabase's pooler in **transaction** mode does not
  support it; **session** mode and the direct connection do. Getting this wrong
  fails silently — pickups simply never appear on anyone's screen.

Then collect two connection strings from Project Settings → Database:

| Variable | Which string | Used by |
|---|---|---|
| `ADMIN_DATABASE_URL` | the owner (`postgres`) connection | `init_db()` only — creates tables and the `auth_lookup` function |
| `DATABASE_URL` | the same host, with user `kikar_app` and its password | every request |

Both must be **session mode or direct**, not transaction mode.

> **Lo que hay hoy no es esto.** En el servicio que está corriendo las dos
> variables tienen el **mismo** valor (`kikar_app`), así que `init_db()` corre
> con el mismo rol que los requests. No es un agujero de aislamiento —
> `tenancy.py` aplica `FORCE ROW LEVEL SECURITY`, que hace que las policies
> apliquen incluso al dueño de las tablas— pero la separación de privilegios que
> esta tabla describe no existe. Si lo cambiás, cambialo en los dos lados.

---

## 2. Render

Render deploys from GitHub; nothing needs to be pushed to it by hand. Point the
service at the repo and the **`main`** branch. `render.yaml` already carries the
build (pip + npm + vite), the start command, and the health check.

**Creá el servicio desde el Blueprint, no a mano.** Un servicio creado a mano no
hereda nada de `render.yaml`: se queda con el start command por default
(`gunicorn app:app`, que acá no existe — el módulo es `server.app`) y sin el
paso de `npm run build`, así que ni arranca ni tendría frontend si arrancara.
Y si ya existe un servicio con el nombre que declara el blueprint, Render le
agrega un sufijo aleatorio al nuevo en vez de fallar — que es exactamente cómo
terminamos con dos.

Set these in the dashboard — **not in the repo**, since several are secrets:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the `kikar_app` connection string |
| `ADMIN_DATABASE_URL` | the owner connection string |
| `ADMIN_EMAIL` | who the first organization's administrator will be |
| `ADMIN_INITIAL_PASSWORD` | leave unset to have one generated and printed once in the logs |
| `SUPERADMIN_EMAIL` | the Kikar platform account; omit and no superadmin is created |
| `SUPERADMIN_INITIAL_PASSWORD` | same as above |
| `ALLOWED_ORIGINS` | every origin the app is served from — today `https://afterschool.kikarlabs.com,https://kikar-afterschool-tunz.onrender.com` |
| `BASE_URL` | the public URL — `https://afterschool.kikarlabs.com`. Without it, every invitation and reset link points at `http://localhost:5000` |
| `JWT_SECRET_KEY` | generated by `render.yaml` |
| `FORCE_HTTPS` | `true`, already in `render.yaml` |
| `RESEND_API_KEY` | needed before invitations can send — `resend` is the default provider |
| `EMAIL_FROM` | the platform fallback sender — `noreply@kikarlabs.com`. Used only for mail that belongs to no organization; each JCC sends from its own address (below). Defaults to `noreply@kikarlabs.com` |
| `EMAIL_SENDER_DOMAIN` | the domain every organization sends from — `kikarlabs.com`, and it must be verified in Resend or every send comes back 403. Defaults to `kikarlabs.com`, so in practice leave it unset |

For the legacy SMTP path instead, set `EMAIL_PROVIDER=smtp` plus `EMAIL_USER`
and `EMAIL_PASS` — note `EMAIL_PASS`, not `EMAIL_PASSWORD`.

### Each organization has its own sender

A JCC does not need a domain of its own. Resend verifies domains rather than
addresses, so with `kikarlabs.com` verified every `*@kikarlabs.com` sends with
no further setup, and each organization gets `{slug}@kikarlabs.com` with its own
name as the display name — `JCC of Northern Nevada <jccns@kikarlabs.com>`. That
happens with nothing configured: the slug is the fallback local part.

Three optional columns on `organizations` override it, all of them writable
**only** through `PATCH /api/superadmin/organizations/<id>` and surfaced in the
platform console under *Outgoing email*:

| Column | Effect when NULL |
|---|---|
| `email_from_local` | falls back to the slug |
| `email_from_name` | falls back to the organization's name |
| `email_reply_to` | no Reply-To header, so replies reach nobody |

`email_from_local` holds the part before the `@` and nothing else — the domain
is appended by the application, which is what makes it impossible for one JCC
to send as another's domain or as Kikar's. Set `email_reply_to` to the JCC's own
address; it is the one field that points off our domain, and without it a parent
who hits reply is writing to a mailbox that does not exist.

`PARENT_INVITES_ENABLED=1` is what actually turns invitations on. Leave it off
until the email sender is configured and verified, or the first bulk send fails
against every parent at once.

## 3. Read the boot log

Three lines decide whether the deploy is sound:

```
[tenancy] Row level security is enforced for this connection.
```
Anything else here means `DATABASE_URL` is pointing at a role with BYPASSRLS
and tenant isolation is relying on application scoping alone.

```
VAPID keys loaded from database
```
Push notifications have a keypair. On the very first boot it generates and
stores one instead.

```
[SECURITY] Generated initial admin password...
```
Only appears when `ADMIN_INITIAL_PASSWORD` was left unset. It is printed once
and never again — capture it before the log rolls.

---

## 4. Verify

```
GET  https://<your-app>/api/health        -> {"status":"ok"}
GET  https://<your-app>/app/login         -> the sign-in screen
```

Then sign in as the superadmin and create the first real organization.

### What the free instance cannot show you

Free spins down after ~15 minutes idle, and that kills every open SSE stream
and the LISTEN/NOTIFY listener thread. Live pickup only works while the service
is warm, and the first request after a lull takes 30-60 seconds. That is fine
for checking the app deploys and signs in; it is not a fair test of the pickup
queue, and it is not something a parent waiting at the curb should ever meet.
Move to a paid instance before real families use it.
